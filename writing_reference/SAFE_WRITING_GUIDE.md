# SAFE_WRITING_GUIDE

> **用途**：数学建模竞赛论文写作速查手册。  
> **来源边界**：仅由以下三份历史写作研究提炼：
> - `additional_official_excellent_2015_structure.md`
> - `writing_structure_2016_2018.md`
> - `writing_structure_2019_2021.md`
>
> **不使用**：2022 年及之后的当前赛题赛后论文、讲评、题解或路线信息。  
> **定位**：本文件只决定“已经完成的模型与结果应该怎样表达、组织和核查”，不反过来改变已经冻结的数学模型。

---

# 0. 一句话总原则

高质量竞赛论文不是“模型名很多”，而是形成一条连续、可核查的证据链：

> **做什么 → 为什么这样建 → 怎样算 → 算出什么 → 凭什么相信 → 在什么条件下成立。**

对每个小问，最稳妥的局部闭环是：

> **小问目标 → 关键困难 → 必要假设 → 变量与机制 → 数学模型 → 求解算法 → 核心结果 → 一种独立检查 → 本问小结。**

论文可以没有多个复杂模型，但不应跳过“关键困难”和“独立检查”。

---

# 1. 使用方法

本 Guide 不是论文模板库，也不是模型选择器。

使用顺序：

1. 模型、代码、正式结果已经完成；
2. 先确定本问要直接回答什么；
3. 再用本 Guide 选择叙事、公式、图表和验证；
4. 所有正式数字必须来自正式结果文件，不手工改数；
5. 写作不能把“模型内部输出”包装成“现实事实”；
6. 如果证据不足，降低结论强度，而不是靠措辞补强。

---

# 2. 摘要：写成“压缩版答卷”

## 2.1 摘要必须给答案，不只是报方法名

推荐结构：

1. 1 句说明对象、目标和最主要困难；
2. 每个小问 1—2 句：
   - 状态/变量或关键机制；
   - 模型或关系；
   - 求解/验证方法；
   - 最关键结果；
3. 1 句说明最重要的验证与适用边界；
4. 关键词优先写问题结构和核心方法。

每问最小单元：

> **任务/困难 + 建模动作 + 求解方法 + 核心结果 + 结果性质。**

不要写成：

> “针对问题一使用 A 模型，问题二使用 B 算法，问题三使用 C 软件。”

更好的逻辑是：

> “针对某个具体困难，引入什么状态或约束，建立什么关系，怎样求解，最终得到什么关键结果。”

## 2.2 摘要数字原则

只放决定性数字或规律。

不要把完整参数表、所有工况结果、所有算法名塞进摘要。

摘要中的数字必须与正文最终结果一致，并明确它属于哪一种：

- 观测值；
- 模拟值；
- 预测值；
- 模型内部估计；
- 理论保证。

高精度小数不会自动增加可信度。

---

# 3. 问题重述与问题分析：职责必须分开

## 3.1 问题重述回答“题目是什么”

只保留：

- 研究对象；
- 输入；
- 输出；
- 约束；
- 各小问之间的关系。

不要大段复制原题。

## 3.2 问题分析回答“为什么这样建”

每问至少提前回答：

- 真正的输入、状态、决策和输出是什么？
- 最难的地方是什么？
- 从上一问继承什么？
- 本问新增了什么：信息、约束、随机性、误差、参与者还是实验因素？
- 为什么需要这种模型或简化？
- 用什么证据判断这一问做成功了？

如果“问题分析”只是把“题目要求建模”改写为“因此我们建立模型”，应删除。

## 3.3 推荐的路线表

可以用一张很小的表：

| 小问 | 核心困难 | 继承内容 | 新增结构 | 求解接口 | 主要验证 |
|---|---|---|---|---|---|

这张表的作用是给读者导航，不是堆模型名称。

---

# 4. 多问之间怎样形成自然递进

优秀论文不要求机械写成“基线模型—改进模型—创新模型”。

更自然的递进至少有三类：

## 4.1 假设递进

> 理想情形 → 放宽一个假设 → 再加入现实约束 → 控制或优化。

关键句必须回答：

> **上一层模型漏掉了什么？本层为什么只增加这一项？**

## 4.2 信息递进

> 核心状态不变 → 信息结构改变 → 决策规则随信息改变。

例如同一套状态、资源账本或评价指标被后问复用，只新增随机性、玩家或未知信息。

## 4.3 证据递进

> 描述规律 → 判断因素 → 优化/预测 → 新实验或独立检查。

适合统计、数据与实验型问题。

## 4.4 跨问复用优先

如果后一问能够继承前一问的：

- 状态；
- 变量；
- 机制；
- 指标；
- 约束；
- 程序接口；

优先复用，而不是每问换一套互不相干的算法。

---

# 5. 假设与符号：把它们当作风险清单

## 5.1 每条重要假设至少说明四件事

| 字段 | 要回答的问题 |
|---|---|
| 假设 | 具体忽略或固定了什么？ |
| 理由 | 为什么在本问范围内可以这样做？ |
| 影响 | 可能让结果偏高、偏低或只在局部成立吗？ |
| 检查 | 用什么边界情形、参数扰动或扩展模型检查它不致命？ |

不要只写“为了简化计算，作如下假设”。

## 5.2 符号表原则

重要符号要有唯一、可追踪定义。

至少包含：

- 符号；
- 含义；
- 单位或取值域。

必要时增加数据来源。

不要为了显得专业而把只出现一次的符号全部塞进总表。通用高频符号集中列，局部符号可以在相应小问就地定义。

---

# 6. 公式段：先语义，后形式，再回到题目

一个完整公式段推荐按以下顺序：

1. **现实/数学来源**：这条关系为什么存在？
2. **变量定义**：变量、索引、单位、合法范围是什么？
3. **数学表达**：给出公式；
4. **初值/边界/约束**：什么情况下可行？
5. **求解方式**：怎样得到数值或解？
6. **输出解释**：公式输出代表什么？
7. **回到题目**：它怎样回答当前小问？
8. **必要时小例**：用极小例子或边界情形检查公式行为。

特别是优化题，不能只给目标函数；必须同时明确：

- 优化方向；
- 决策变量；
- 变量边界；
- 关键约束；
- 可行性复核。

---

# 7. 算法段：写“本题接口”，不要写教科书历史

算法段最需要交代的是：

1. 输入是什么；
2. 状态或解向量怎样编码；
3. 候选/动作怎样产生；
4. 可行性在哪一步检查；
5. 目标函数或评分怎样计算；
6. 更新规则是什么；
7. 何时停止；
8. 返回什么；
9. 它是精确、容差最优、启发式还是随机方法；
10. 输出怎样进入论文结果表。

## 7.1 什么时候需要流程图

只有存在明显的：

- 多分支；
- 多状态；
- 循环；
- 回溯；
- 终止判断；

才值得画流程图。

简单解析计算不必为了“看起来复杂”硬塞流程图。

## 7.2 随机算法

至少说明：

- 随机种子或种子策略；
- 重复次数；
- 汇报均值、分位数、标准差或最差结果中的适当项；
- 不要只挑最好的一次。

## 7.3 不要把通用算法介绍写太长

“模拟退火来自固体降温”“粒子群模拟鸟群”等背景，对本题可信度帮助很小。

正文空间应优先给：

> **状态、候选、约束、目标、终止、输出。**

---

# 8. 结果段：先直接回答，再解释

结果出来后，不要先放一大堆图。

推荐顺序：

1. 一句话直接回答本问；
2. 主表给核心数字或方案；
3. 一张图解释机制、过程或空间关系；
4. 一项独立核查；
5. 解释收益、代价和适用范围。

## 8.1 推荐的最小结果包

> **一个主表 + 一张解释图 + 一项核查。**

### 主表

承担精确证据：

- 最终决策；
- 参数；
- 核心指标；
- 对照方案；
- 必要的可行性信息。

### 解释图

承担机制证据：

- 路线；
- 曲线；
- 空间姿态；
- 状态变化；
- 残差；
- 多情景差异。

### 核查

可以是：

- 题面阈值；
- 手算小例；
- 基线比较；
- 小规模穷举；
- 理论上下界；
- 参数敏感性；
- 留出数据；
- 独立程序；
- 极端/边界情形。

---

# 9. 图表：一张图只回答一个问题

正文中的每一张图都要能回答：

> **读者应该从这张图判断什么？**

常见职责：

| 类型 | 主要职责 |
|---|---|
| 结构/几何图 | 解释模型对象、坐标、状态或机制 |
| 流程/状态图 | 解释“怎么算” |
| 结果图 | 展示过程、路线、空间或参数规律 |
| 诊断图 | 发现残差、误差、边界或异常 |
| 多情景图 | 同口径比较多个条件 |
| 结果表 | 给精确数字、方案和指标 |

图后建议立即写：

1. 看到了什么趋势；
2. 为什么会出现；
3. 是否改变最终决策。

不要：

- 一张图塞太多职责；
- 画大量只换一个参数的重复曲线；
- 用漂亮思维导图代替真正模型结构；
- 用饼图替代需要精确比较的结果表；
- 把拟合图或收敛图直接称为独立验证。

---

# 10. 验证：必须尽量换一种证据口径

“模型评价”不是“模型验证”。

以下都不能单独证明模型正确：

- “结果符合实际”；
- “图像符合直觉”；
- “算法收敛了”；
- “训练拟合很好”；
- “我们未来还可以做实验”。

## 10.1 验证证据从弱到强

可按任务选用：

1. 可视化/常识检查；
2. 控制变量或参数扫描；
3. 敏感性、极端情景、反例；
4. 多基线同口径比较；
5. 小规模穷举或精确解；
6. 理论上下界或数学保证；
7. 外部数据、留出集或真实试验。

高质量结果最好至少有两种不同口径的证据。

例如：

- 基线比较 + 小规模精确解；
- 敏感性 + 理论上界；
- 留出集 + 参数稳定性。

如果主实现、结果生成和“验证”完全共用同一个函数，它们可能一起错。

## 10.2 验证与结论必须匹配

验证能支持什么，就写到什么程度。

不能因为：

- 求解器返回了一个数，就写“全局最优”；
- 收敛曲线变平，就写“全局收敛”；
- 模拟路线符合直觉，就写“所有约束满足”；
- 训练拟合好，就写“预测可靠”；
- 自建仿真改善，就写“现实系统一定改善”。

---

# 11. 创新：不要为了“有创新”强行增加模型

内部工作可以有最小基线，但论文外部不必机械设置：

> 基线模型 → 改进模型 → 创新模型

只有在复杂方法确实需要被证明“值得”时，才重点写基线对比。

## 11.1 什么时候值得写基线

- 新算法声称提高收益、精度或效率；
- 简单规则已有可比较结果；
- 需要证明复杂算法确有必要；
- 随机/启发式方法需要精确小例作参照。

## 11.2 更稳妥的创新判断三问

1. 基础方法具体在哪种情形失败？
2. 新增结构是否针对这个失败？
3. 有没有同口径证据说明缺陷得到缓解？

如果三问答不出来，不要单独写“创新性强”。

创新可以来自：

- 更合理的状态表达；
- 更清晰的模型复用；
- 针对真实失败的约束或机制；
- 独立验证；
- 更可复算的结果结构；
- 把现实可实施性写入目标或约束。

不是模型越多越创新。

---

# 12. 结论强度：证据有多强，措辞就有多强

推荐始终区分：

- 观测；
- 模拟；
- 预测；
- 模型内部估计；
- 理论保证。

## 12.1 常见安全措辞

当只有程序得到可行结果时：

> “得到一组满足给定约束的可行方案。”

当只证明在测试场景优于基线：

> “在本文设定的同口径测试条件下优于基线。”

当结论来自局部分析：

> “在目标邻域/给定假设下成立。”

当小规模可穷举：

> “在该小规模实例上与全枚举最优值一致。”

当有理论保证：

> 明确写出保证成立的假设与范围。

## 12.2 高风险词

以下词必须有对应证据才能使用：

- 全局最优；
- 必然；
- 唯一；
- 因果；
- 显著；
- 稳健；
- 普适；
- 完全正确；
- 精度高；
- 运行快。

不要用“算法先进、模型严谨、考虑全面”等自我评价替代证据。

---

# 13. 模型评价与局限：写真实风险，不写套话

优点必须对应前文已经展示的证据。

例如：

- 有独立小例对照，才能说“实现经过独立核查”；
- 有跨情景测试，才能说“在这些情景下稳定”；
- 有运行时间数据，才能说“计算效率较高”。

局限应具体到：

- 哪条假设；
- 哪个数据范围；
- 哪个参数；
- 哪个已观测失败；
- 哪个仍未验证环节；
- 哪个结论只能局部成立。

优先写：

> “该假设可能导致什么偏差，以及我们做了什么检查。”

不要只写：

> “模型仍有改进空间。”

---

# 14. 附录与支撑材料：承担“复现接口”

附录不是代码仓库。

正文只保留：

- 核心公式；
- 关键伪代码；
- 必要算法接口；
- 核心结果。

支撑材料最好能回答：

- 哪个程序生成哪个结果？
- 输入数据在哪里？
- 正式结果文件在哪里？
- 图表由哪个脚本生成？
- 随机种子和参数是什么？
- 运行入口是什么？

推荐最小接口：

```text
README
data / input
src
tests
results
figures
```

如果已有项目结构，不必为了论文重新建目录；核心是“结果可追踪”。

---

# 15. 每个小问的标准正文闭环

对每问优先按下面顺序组织：

## 15.1 本问目标

- 题目到底要输出什么？
- 成功指标是什么？

## 15.2 继承与新增

- 从前问继承什么？
- 本问新增什么困难？

## 15.3 建模

- 必要假设；
- 变量与机制；
- 目标与约束；
- 核心公式。

## 15.4 求解接口

- 输入；
- 状态/解向量；
- 算法步骤；
- 可行性检查；
- 停止条件；
- 输出。

## 15.5 结果包

优先：

> **一个主表 + 一张解释图 + 一项核查。**

## 15.6 证据与边界

- 证据属于什么口径？
- 能支持什么结论？
- 不能支持什么结论？
- 哪些条件下可能失效？

## 15.7 一句话小结

必须直接回答当前小问，而不是重复“建立了模型”。

# 16. 为执行流程新增的 Paper Handoff 模板

> 说明：`Paper Handoff` 是项目执行层的操作化名称，不是历史论文中的固定术语。下面模板由上述“分问闭环、结果包、验证与追溯”原则整理而成。

每个小问正式结果完成后，可生成：

```markdown
# QX PAPER HANDOFF

## 1. 一句话直接答案
本问最终回答是什么？

## 2. 在全题中的作用
继承前问什么？
向后问提供什么？

## 3. 推荐叙事
选择：
- 假设递进
- 信息递进
- 证据递进
- 独立分问闭环
- 共用框架复用

并说明为什么。

## 4. 核心数学
### MAIN_TEXT
正文必须出现的公式/定义。

### APPENDIX
适合放附录的推导/程序细节。

### OMIT
不值得进入论文的调试过程或重复公式。

## 5. 结果包
- 主表：
- 解释图：
- 核查：

## 6. 证据性质
分别标记：
- 内部一致性
- 实现交叉检查
- 独立检查
- 敏感性/边界
- 理论保证
- 外部/留出证据（如有）

## 7. 结论强度
### 可以写
...

### 不应写
...

## 8. 创新/贡献
回答：
1. 基础处理的具体缺口是什么？
2. 本问新增了什么结构？
3. 有什么同口径证据说明它有价值？

若没有独立创新：
NO_SEPARATE_INNOVATION_CLAIM

## 9. 给论文作者的段落级提纲
P1：
P2：
P3：
P4：
...

## 10. 来源接口
- 正式结果文件：
- 代码入口：
- 验证文件：
- 图表数据：
- 关键文献：

## 11. 剩余写作风险
- 缺少什么证据？
- 哪个参数理由还需说明？
- 哪个 claim 必须降级？
- 哪张图仍需生成？
```

Paper Handoff 的作用是把“模型执行”翻译成“论文可写材料”，不是重新开题。

# 17. 提交前快速检查表

## 摘要

- [ ] 每个小问都有方法和结果，不只有模型名。
- [ ] 摘要数字与正文正式结果一致。
- [ ] 观测、模拟、预测、模型估计、理论保证已区分。

## 问题分析与模型

- [ ] 问题分析说明了为什么这样建。
- [ ] 各问之间的继承关系清楚。
- [ ] 每条关键假设有理由、影响和检查。

## 算法

- [ ] 有输入、输出、状态/解向量、步骤、更新和停止。
- [ ] 已说明精确、启发式、随机或局部性质。
- [ ] 可穷举的小规模问题已尽量做精确对照。
- [ ] 随机试验不是只报最好一次。

## 结果与图表

- [ ] 每张图只承担一个主要论证任务。
- [ ] 图后正文明确告诉读者看什么。
- [ ] 主结果优先有表格。
- [ ] 比较使用同数据、同约束、同指标和同随机性口径。

- [ ] 关键数字来自同一正式结果链，不手填。
- [ ] 优化结果逐项通过变量范围和约束检查。

- [ ] 至少有一种与主实现不同口径的检查。
- [ ] 没有把收敛曲线当作全局最优证明。
- [ ] 没有把训练拟合当作预测验证。

## 附录与追溯

- [ ] 正文结果能定位到结果文件。

# 18. 给 Codex / Work 的使用规则

1. 本文件只用于**写作与证据组织**，不得反过来修改已冻结模型。
2. 模型执行阶段不必频繁读取历史写作资料；需要 Paper Handoff 时优先读取本文件。
3. 不因为“论文需要创新”而新造算法。
4. 不因为“论文需要验证”而把同一个程序再跑一遍就称为独立验证。
5. 不因为“摘要需要结果”而手工填正式数字。
6. 不因为“论文要高级”而堆模型名、算法背景或复杂流程图。
7. 若写作结构与正式结果冲突，以正式结果和模型证据为准。
8. 若证据不足以支撑强结论，降低 claim，不修饰事实。
9. 每个小问优先形成：
   > **直接答案 + 主表 + 解释图 + 独立核查 + 适用边界。**
10. 全篇优先保持一条贯穿各问的主线，而不是追求模型数量。

# 19. 最后记住三件事

## 1. 主线比模型数量重要

后一问必须让读者看得出：

> **继承了什么，新增了什么，为什么新增。**

## 2. 证据包比“高级算法感”重要

一个复杂算法如果没有基线、边界、小例或独立检查，并不会因为名字高级而更可信。

## 3. 语气必须和证据同级

区分：

> **代码输出 ≠ 模型内部预估 ≠ 外部验证 ≠ 理论保证。**

论文最重要的不是把结果写得“很强”，而是让评阅者清楚知道：

> **结果是什么、从哪里来、为什么可信、可信到什么程度。**
